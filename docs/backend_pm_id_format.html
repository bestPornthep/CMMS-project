PM Task ID Format Redesign

Replaces the current PM-XXX-0001 pattern (CmmsService.generateTaskId()) with an ID that embeds the machine and PM period directly, and a sequence number that grows safely over a 10+ year system lifetime.

1. New format

PM- {MachineID}- {PeriodCode}- {Seq}
SegmentMeaningExample
PMFixed literal prefixPM
{MachineID}The asset's own ID, unchanged, dashes and all (already unique)FCT-RN005-AR-A-001
{PeriodCode}Short code for the PM's frequency — see table below1m
{Seq}Occurrence number of this machine+period series, never resets, digit width grows naturally01

Full example: PM-FCT-RN005-AR-A-001-1m-01 → second monthly occurrence is PM-FCT-RN005-AR-A-001-1m-02, 13th is ...-1m-13.

2. Period codes

Derived from PMSchedule.frequency (free text today — see PMTaskFrequency in the frontend model). Express everything in its smallest natural unit; no separate "quarterly"/"yearly" letter.

Custom "N Hour(s)"{N}h

Reuse the existing FREQUENCY_ALIASES normalization already in pm.service.ts (e.g. "3 month(s)" ≡ Quarterly) so a custom duration numerically equal to a preset gets the same period code as the preset, not a different-looking ID for the same thing.

3. Sequence number — the part that must survive 10 years

Rules

  1. Scope: one counter per (assetId, periodCode) pair — matches the existing invariant that an asset has at most one active PM per frequency.
  2. Starts at 1, formatted String(n).padStart(2, '0') — i.e. minimum width 2, but never truncated: 1→01, 12→12, 100→100, 4380→4380. No fixed digit count anywhere in code — this is what makes 3/4/5-digit growth automatic instead of a future migration.
  3. Never resets — not per calendar year, not on machine deactivate/reactivate. A reactivated machine's next task continues from its last number (e.g. paused after 12, resumes at 13).
  4. Only increments when a new task occurrence is actually generated (by the create flow or the nightly scheduler) — never pre-reserved in bulk.

4. Counter storage & concurrency

New table, e.g. cmms_pm_id_sequences:

assetId     varchar   (FK -> cmms_assets.id)
periodCode  varchar
lastSeq     int       default 0
PRIMARY KEY (assetId, periodCode)

Generate the next number with a single atomic statement inside the same transaction that creates the task — do not read-then-write in two steps:

UPDATE cmms_pm_id_sequences
SET lastSeq = lastSeq + 1
OUTPUT INSERTED.lastSeq
WHERE assetId = @assetId AND periodCode = @periodCode;
-- if no row matched, INSERT (assetId, periodCode, lastSeq=1) instead, then use 1
This must be atomic. The nightly generator already has a known duplication bug (blind insert, no reconcile — see docs/backend_nightly_task_duplication.html). A non-atomic read-modify-write on this counter under concurrent nightly + manual-create runs would hand out duplicate sequence numbers. Fix that bug and this counter with the same transactional discipline.

5. Rollout — no migration needed

Confirmed with user: all PM task rows currently on the dev DB are mock/test data, not real production history. No backfill/rename of existing PM-XXX-0001 IDs is required — the backend can simply start minting the new format for every task created after this change ships, and truncate/reset cmms_pm_tasks + the new sequence table if a clean slate is easier than mixed-format data during dev testing.

6. Frontend status

No frontend change needed to generate IDs — task/schedule IDs are always server-assigned (frontend sends id: '' as a placeholder on create, see pm-create.component.ts). Frontend only displays whatever ID the backend returns, so once this ships server-side, the new format shows up automatically everywhere an ID is rendered (task lists, PDF exports, audit log).
