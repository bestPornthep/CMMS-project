Duplicate PM Type Hard Block — Backend Requirements

v2 — an asset may only ever have one PM per frequency, full stop. Frontend already enforces this as a best-effort UX check; this doc specifies the authoritative server-side enforcement that must exist so the rule can't be bypassed by a direct API call or a race between two users.

This also simplifies the DB fix — no filtered/partial index needed, just a plain unique constraint.

1. Business Rule

For a given assetId, at most one PM series/task of a given frequency may ever exist. Status is not part of the check — a PMTask row for that assetId + frequency blocks a new create request regardless of whether it's Pending, In Progress, Pending Approval, Overdue, or Done.

Existing task status for same assetId + frequencyNew create request
Pending❌ Hard blocked
In Progress❌ Hard blocked
Pending Approval❌ Hard blocked
Overdue❌ Hard blocked
Done❌ Hard blocked
No matching task exists✅ Allowed

Matching is on the exact frequency string (e.g. Monthly, Quarterly, or a custom value like 3 month(s)) — two different frequencies on the same asset (e.g. one Monthly PM + one Quarterly PM) are not duplicates and both are allowed. Two different PM titles/checklists at the same frequency on the same asset are considered duplicates under this rule (title/checklist content is not part of the uniqueness key) — confirm with product owner if a finer-grained key (e.g. + title) is ever needed later; as specified today it's asset + frequency only.

2. Endpoint to Guard

POST /api/v1/pm-tasks/schedulePOST — recurring series creation. Also applies to the one-time-task path (POST /api/v1/pm-tasksPOST) since a single one-time PM occupies the same "slot" for that asset+frequency, permanently, once created.

Both endpoints must run the same check: reject with 409 Conflict if any task already exists for the submitted assetId + frequency, regardless of its status. There is no override/force flag — this is a hard block for every role (Admin, Manager, Engineer, Technician all equally blocked; this is a data-integrity rule, not a permission rule).

3. Race-Condition Safety (critical)

2026-09-13 addition — Custom-duration equivalence: a user can pick Custom and type a duration that's numerically identical to a preset (e.g. 1 month(s) == Monthly, 3 month(s) == Quarterly, 12 month(s)/1 Year(s) == Yearly, 7 day(s) == Weekly, 1 day(s) == Daily). These must be blocked as duplicates too, or the whole hard-block is trivially bypassed by choosing Custom instead of the preset dropdown. Apply the same alias mapping used by the frontend (pm.service.ts FREQUENCY_ALIASES) server-side before comparing. Any other custom value/unit combination (e.g. 2 month(s), 6 hour(s)) has no preset equivalent and is only a duplicate of another identical custom value.
2026-09-13 addition — case/whitespace normalization: the frontend's duplicate check compares frequencies after .trim().toLowerCase(), applied unconditionally (not just when an alias-table match is found) — so "Monthly", "monthly", and " Monthly " are all treated as the same value. The backend's normalizedFrequency must do the same (lowercase + trim every value, alias hit or not) — if the backend only lowercases the 6 known alias keys and leaves everything else in its original casing, a frontend/backend mismatch becomes possible: the frontend blocks a case-variant duplicate that the backend's unique constraint would silently allow through (or vice versa).
Open question — hour-based aliases: the frontend's custom-duration dropdown also offers an hour(s) unit, but FREQUENCY_ALIASES currently has no hour-based entries. 24 hour(s) (exactly 1 day) and 168 hour(s) (exactly 7 days) are the same class of exact, calendar-independent equivalence already covered for day/month/year — they may simply have been missed rather than deliberately excluded. Confirm with the frontend/product owner whether these should be added to the shared alias mapping before backend implements it, so both sides stay in sync.
Do not implement this as a plain "SELECT to check, then INSERT if nothing found." That has a TOCTOU (time-of-check-to-time-of-use) gap: if an Engineer and a Manager both submit "Create Monthly PM for Asset A" within the same moment, both requests can pass the SELECT check before either one's INSERT commits, and you end up with two active Monthly series on the same asset anyway — silently defeating the whole point of this feature.

Use one of these (in order of preference):

  1. Database constraint (preferred): because of the Custom-duration equivalence rule above, the unique constraint can't simply be on the raw frequency column ("1 month(s)" and "Monthly" are different strings but must collide). Add a computed/stored normalizedFrequency column (populated via the same alias mapping plus lowercase+trim on every value at write time) and put the UNIQUE constraint on PMTask (assetId, normalizedFrequency) instead — this keeps the raw frequency label exactly as the user typed it (for display) while still letting the DB atomically reject alias and case-variant duplicates. Works with a normal Prisma @@unique([assetId, normalizedFrequency]). Let the DB reject the second concurrent insert with a constraint violation, and have the controller catch that specific error (e.g. Prisma P2002) and translate it to 409. This is the only option that is correct under concurrency without extra locking.
  2. Transactional check-and-insert with row/table locking: if the normalized column isn't feasible on the current schema, wrap the existence check (using the same normalization) + the task/schedule insert in a single DB transaction using an isolation level (or explicit locking hint, e.g. UPDLOCK/HOLDLOCK in MSSQL) that prevents another concurrent transaction from inserting a conflicting row until this one commits. A default read-committed SELECT inside a transaction is not sufficient by itself.

Either way: the guarantee must hold when two different users, from two different requests/connections, submit at effectively the same instant — this was the exact scenario called out by the user ("I forgot about one machine that was created by Eng and Mgr at the same time").

Migration blocker: adding a UNIQUE constraint fails if any existing data already violates it. Since this rule never existed before, query the live table for existing (assetId, frequency) duplicates first and resolve them (e.g. archive/merge/rename) before the migration can be applied.

4. Error Response Shape

On block, return 409 Conflict with enough detail for the frontend to show a useful message:

{
  "message": "A Monthly PM already exists for this asset.",
  "conflict": {
    "taskId": "TASK-00231",
    "scheduleId": "SCH-00042",
    "assetId": "AST-014",
    "frequency": "Monthly",
    "status": "In Progress",
    "assignedTo": "TECH004"
  }
}

5. Implementation Notes / Edge Cases

  • Applies per assetId, not per product/department — the same asset can't be scoped around by choosing a different product on the create form.
  • Because status no longer matters, this is effectively a permanent one-PM-type-per-asset rule: once a Monthly PM has ever been created for an asset, no one can create another Monthly PM for that same asset again, even after the first is fully Done. This is an intentional simplification per user request — flag it back to the user if a future need arises to "retire" a PM type and start a fresh one on the same asset (there is currently no such escape hatch specified).
  • This check is independent of the reassign feature (docs/backend_pm_reassign_api.html) and the series checklist edit feature (docs/backend_pm_series_checklist_edit.html) — it only fires on create, not on updates to an existing series.
  • Frontend already does a best-effort client-side check (using its already-loaded in-memory task list) purely for instant UX feedback before the request is even sent — that check is not a substitute for this server-side enforcement and can be stale (e.g. another user created a conflicting PM after this client's data was last loaded).
