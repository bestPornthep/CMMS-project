PM Create: User-Chosen Start Date — Backend Requirements

New: the user picks the exact due date of the first PM occurrence on Create PM, instead of it always defaulting to today + 1 interval.
  • 1. Business Rule
  • 2. Changed Endpoint: POST /api/v1/pm-tasks/schedule
  • 3. One-Time Task (no change)
  • 4. Implementation Notes / Edge Cases

1. Business Rule

The user-chosen startDate becomes task #1's exact due date — no interval offset applied to it. Every later occurrence in the series is still startDate + N×frequency, same math as today.

PM TypeStart DateTask #1 dueTask #2 dueTask #3 due
Monthly30 Aug 202630 Aug 202630 Sep 202630 Oct 2026
Weekly3 Sep 20263 Sep 202610 Sep 202617 Sep 2026

Restriction: startDate must be today or later — no backdating. Validate on both frontend (already done) and backend (defense in depth).

2. Changed Endpoint: POST /api/v1/pm-tasks/schedule POST

File: backend/src/pm-tasks.controller.ts, method createSchedule(). No new endpoint — same route, new optional body field.

Request body (new field)

{ ..., "startDate": "2026-08-30" }  // optional, ISO date string

Handler change

// existing:
const dates = this.cmms.calculateDates(body.frequency);

// new:
const startDate = body.startDate ? new Date(body.startDate) : new Date();

const today = new Date();
today.setHours(0, 0, 0, 0);
if (startDate < today) {
  throw new BadRequestException('Start date cannot be in the past');
}

const dates = [startDate, ...this.cmms.calculateDates(body.frequency, startDate)];
Why this is safe: calculateDates(frequency, startDate) already returns startDate + 1×interval, startDate + 2×interval, … when given a startDate — that's its existing, unchanged contract. Prepending startDate itself gives exactly "task #1 = start date, task #2 = start + 1 interval, …" without touching calculateDates(). SchedulerService.topUpSchedules() calls calculateDates() the same way it always has (with startDate = latestTask.nextDueDate, expecting only future occurrences back) — completely unaffected by this change.

Everything else in createSchedule() (creating the PmSchedule row, the [SeriesID: xxx] marker, looping createTaskWithRetry() per date) stays as-is; only the dates array's construction changes.

3. One-Time Task (no change)

POST /api/v1/pm-tasks (create()) needs no backend change — it already persists whatever nextDueDate the request body sends. The frontend now sends the user's chosen start date directly instead of a pre-offset one.

4. Implementation Notes / Edge Cases

  • Backward compatible: body.startDate is optional — omitting it falls back to new Date(), identical to today's behavior. No existing caller breaks.
  • Timezone: compare dates at day granularity (zero out time-of-day) when checking "today or later", same pattern as scheduler.service.ts's markOverdueTasks() date comparisons, to avoid same-day rejections from time-of-day drift.
  • No schema change needed — startDate isn't persisted as its own column; it's just the anchor used once at generation time. Each generated PmTask row already stores its own nextDueDate.
  • No change needed to SchedulerService.topUpSchedules() or cmms.service.ts's calculateDates() — both keep their exact current behavior/contract.
