PM Task Reassignment (Series Cascade) — Backend Requirements

v2 — supersedes the earlier single-task-only version. New in this version: reassigning one occurrence now cascades to every still-Pending future occurrence in the same recurring series, plus the series' default assignee, in one atomic operation.
  • 1. Business Rule — which statuses allow reassign
  • 2. Cascade Behavior (new)
  • 3. New Endpoint: PUT /api/v1/pm-tasks/:id/reassign
  • 4. Schema Change (new column)
  • 5. Implementation Notes / Edge Cases

1. Business Rule

Current status of the clicked occurrenceReassign allowed?Why
PendingN/ANot yet started — this is the existing "Assign" flow, not reassign.
In Progress✅ YesNormal case — swap the technician mid-task, and roll the change forward through the series.
Overdue✅ YesAlways unassigned when reached (see scheduler.service.ts markOverdueTasks()) — behaves like a first assign for this one row, but still cascades to future Pending siblings.
Pending Approval❌ NoWork already submitted for approval — don't change the credited technician.
Done❌ No — hard blockedAlready approved, must stay immutable.

2. Cascade Behavior (new)

Reassigning one occurrence in a recurring series now updates three things in one atomic transaction:

#What updatesFields written
1The clicked occurrence itself (the primary target of the request)assignedTo, assignedAt = now, assignedBy, reassignCount += 1
2Every other occurrence in the same series that is still status = 'Pending' (i.e. every future month/week/day already pre-generated by createSchedule()/topUpSchedules() that hasn't been touched yet)assignedTo, assignedBy, reassignCount += 1. Not assignedAt — these rows aren't actually starting work, they're just being re-labeled with the new default technician; see §5.
3The PmSchedule row for this series (if one exists — see legacy note in §5)assignedTo — so the nightly topUpSchedules() cron generates future new rows (beyond whatever is already pre-generated) with the new technician too, not the old one.
What is never touched: any occurrence in the series that is already Done (approved history) or currently In Progress/Pending Approval other than the one explicitly clicked (this shouldn't normally exist per the "assign one occurrence at a time" flow, but if it ever does, it's left alone — only the explicitly-targeted occurrence and untouched Pending siblings are affected).

3. New Endpoint: PUT /api/v1/pm-tasks/:id/reassign PUT

File: backend/src/pm-tasks.controller.ts. This is a new, dedicated endpoint rather than folding cascade logic into the existing generic update() handler — the cascade is a genuine multi-row transaction with side effects (schedule update, audit log) that should only ever fire for this one specific action, never accidentally from an unrelated generic field edit.

Request body

{ "assignedTo": "TECH-042" }

Handler logic

const existing = await prisma.pmTask.findUnique({ where: { id } });
if (!existing) throw new NotFoundException();

// same canAssign check the generic update() handler already uses
if (!canAssign) throw new ForbiddenException();

if (existing.status === 'Done') {
  throw new ForbiddenException('Cannot modify a completed task');
}
if (!['In Progress', 'Overdue'].includes(existing.status)) {
  throw new ForbiddenException(`Cannot reassign a task in '${existing.status}' status`);
}
if (body.assignedTo === existing.assignedTo) {
  throw new BadRequestException('Task is already assigned to this technician');
}

const oldTechId = existing.assignedTo;

const seriesWhere = existing.scheduleId
  ? { scheduleId: existing.scheduleId, status: 'Pending', id: { not: existing.id } }
  : extractSeriesIdFromDescription(existing.description)
    ? { description: { contains: `[SeriesID: ${seriesId}]` }, status: 'Pending', id: { not: existing.id } }
    : null; // standalone task, no series to cascade to

const [updatedPrimary, cascadeResult] = await prisma.$transaction(async (tx) => {
  const primary = await tx.pmTask.update({
    where: { id: existing.id },
    data: { assignedTo: body.assignedTo, assignedAt: new Date(), assignedBy: user.employeeId, reassignCount: { increment: 1 } },
  });

  const cascade = seriesWhere
    ? await tx.pmTask.updateMany({
        where: seriesWhere,
        data: { assignedTo: body.assignedTo, assignedBy: user.employeeId, reassignCount: { increment: 1 } },
      })
    : { count: 0 };

  if (existing.scheduleId) {
    await tx.pmSchedule.update({ where: { id: existing.scheduleId }, data: { assignedTo: body.assignedTo } }).catch(() => {});
  }

  return [primary, cascade];
});

await cmms.logAction(
  `Reassigned ${existing.id}${cascadeResult.count > 0 ? ` + ${cascadeResult.count} future occurrence(s)` : ''} from ${oldTechName(oldTechId)} to ${newTechName(body.assignedTo)}`,
  { id: user.employeeId, name: user.name },
  { id: existing.id, name: existing.title, isUser: false },
  existing.productId, 'data', existing.department,
);

return cleanPmTask(updatedPrimary);

Pseudocode above — adapt to the existing code style/helpers already in pm-tasks.controller.ts (e.g. reuse the same isOwner/hasDelegatedAssign/canAssign computation already at the top of update()).

4. Schema Change (new column)

Add to PmTask in backend/prisma/schema.prisma:

reassignCount  Int  @default(0) @map("reassign_count")

Migration: ALTER TABLE cmms_pm_tasks ADD reassign_count INT NOT NULL DEFAULT 0; — additive, backward compatible, no data migration needed (all existing rows default to 0).

This is what drives the frontend's "Reassign #N" badge in the Assigned PMs tab's new Action column — already wired on the frontend to read task.reassignCount, currently always showing — until this column exists and this endpoint starts incrementing it.

5. Implementation Notes / Edge Cases

  • Why cascaded siblings don't get assignedAt updated: they aren't actually starting work yet — they're future Pending rows just being re-labeled with the new default technician. Only the primary occurrence (the one actually moving/staying In Progress) gets a fresh assignedAt. If this feels wrong once you build it and see real data, flag it — happy to revisit.
  • Legacy series without a PmSchedule row: some older series (created before the createSchedule() fix) have no scheduleId/PmSchedule row, only the [SeriesID: xxx] text marker. Cascade must fall back to matching description contains that marker + status='Pending', same pattern already used in the existing updateSchedule() legacy fallback path. Step 3 (updating PmSchedule.assignedTo) is simply skipped for these — there's no row to update.
  • Standalone (non-series) task: if existing.scheduleId is null and no [SeriesID:] marker is present, cascade is a no-op (only the single primary task updates) — seriesWhere is null, skip the updateMany entirely.
  • One audit log entry per reassignment action, not one per cascaded row — summarized with the affected count, to avoid flooding the PM Audit page.
  • No changes needed to the generic PUT /api/v1/pm-tasks/:id handler for this feature except the still-outstanding "Done tasks are immutable even without status in the body" gap noted in the PM lifecycle review — that's a separate, already-flagged fix, unrelated to this new endpoint.
