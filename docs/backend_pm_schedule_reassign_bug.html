PUT /api/v1/pm-tasks/schedule/:seriesId — Mass-Reassignment Bug Critical

Discovered 2026-08-26 during backend e2e regression testing against the live dev server. Confirmed to have already mutated real data.
  • 1. Confirmed Impact (already happened)
  • 2. Reproduction
  • 3. Root Cause
  • 4. Required Fix
  • 5. Data Recovery
This is not theoretical — it already happened. A single test call with a made-up/nonexistent seriesId reassigned 299 real PM tasks across 10 unrelated recurring series to a single technician, on the live dev server (http://10.144.15.76:3000). There is no application-level audit trail for this field, so the previous assignees cannot be reconstructed without a DB backup/point-in-time restore.

1. Confirmed Impact

Request that triggered it:

PUT /api/v1/pm-tasks/schedule/SCH-does-not-exist
Authorization: Bearer <engineer token>
{ "assignedTo": "TECH-TST-1" }

Expected: no series matches this id → no-op, empty result.

Actual: 200 OK with a large array of updated tasks. Verified via GET /api/v1/pm-tasks?assignedTo=TECH-TST-1 immediately after — 299 tasks across 10 distinct pre-existing series had just been overwritten (all `updatedAt` timestamps matched the exact moment of the one bad request):

2. Reproduction

⚠️ Only run this against a local/disposable DB (e.g. after npx prisma db seed on your own machine). Every run of the final step reassigns every pending task belonging to every real recurring series it can see to whatever assignedTo you send. Do not point $BASE at the shared dev server (10.144.15.76) again.

Prerequisites

  • A local backend running against your own DB (npm run start:dev from backend/), with prisma/seed.ts already applied.
  • At least one real recurring series already existing (e.g. run the app's "Generate PM Schedule" flow once, or call POST /api/v1/pm-tasks/schedule yourself) so you have something to observe getting wrongly touched.

3. Root Cause

This backend checkout is not necessarily the exact version currently deployed on the live server, so the line numbers below are a best-effort match, not a guaranteed diff — but the current source's updateSchedule() in backend/src/pm-tasks.controller.ts has the logic that should apply. Here is the exact request flow it's supposed to follow:

Intended flow (this repo's current source)

1. PUT /pm-tasks/schedule/SCH-does-not-exist received
↓
2. prisma.pmSchedule.findUnique({'{'} where: {'{'} id: seriesId {'}'} {'}'}) — look up a real schedule row
↓ (no row found → schedule is null)
3a. Legacy fallback: pmTask.findMany({'{'} where: {'{'} status:'Pending', description: {'{'} contains: '[SeriesID: SCH-does-not-exist]' {'}'} {'}'} {'}'})expected: 0 rows
↓
4a. if (tasks.length === 0) return [];expected result

What the server actually did (inferred from evidence)

1. PUT /pm-tasks/schedule/SCH-does-not-exist received
↓
2'. Either the schedule lookup, or the task lookup that follows, resolves to far more rows than it should — evidenced by 10 different real scheduleIds all being present in the update resultactual: ~299 rows
↓
3'. Those rows are passed into the update loop (applyScheduleUpdatesToTasks or equivalent) and every one gets assignedTo overwrittenno scoping applied

Step-by-step divergence trace

StepExpectedActual (inferred)
1Schedule lookup by exact idnull (no such row)Unknown — either correctly null (falls to legacy path) or, if the deployed handler doesn't check for null/uses a different lookup, could wrongly resolve to something
2Task lookup where clause{ scheduleId: seriesId, status: 'Pending' } or { description: { contains: '[SeriesID: '+seriesId+']' } } — both scoped to this seriesId onlyEffectively unscoped — matches Pending tasks belonging to 10 unrelated real series
3Empty-result short-circuitif (tasks.length === 0) return [];Never triggered — list wasn't actually empty from the (broken) query's point of view
4Per-task updateNot reached (0 tasks)Runs for all ~299 resolved rows, writing assignedTo to each

Two concrete hypotheses for where step 2 breaks

  • (A) Most likely — stale/pre-fix deployed build. The deployed updateSchedule() may predate the scheduleId-scoped rewrite entirely (see the comment block above createSchedule() in this repo's pm-tasks.controller.ts, which explains a previous fix where a separate, unused PmSchedule-backed controller existed but the frontend never called it). If the deployed version is from before that fix, its task lookup may have no scheduleId/description contains predicate at all — e.g. something as simple as pmTask.findMany({ where: { status: 'Pending' } }) with the seriesId only used for the legacy description-prefix string it writes back, never for filtering what it reads. That single missing predicate alone fully explains "every Pending task in the system gets touched, regardless of the id in the URL."
  • (B) Alternative — ORM/driver-level predicate loss. If the deployed handler logic is byte-for-byte what's shown above, then @prisma/adapter-mssql may be silently dropping the description: { contains: ... } } predicate against the NVarChar(Max) column (rather than throwing). To rule this in/out, capture the actual T-SQL Prisma sends (e.g. DEBUG="prisma:query" env var, or SQL Server Profiler/Extended Events on the DB) for one call and confirm whether a WHERE ... description LIKE N'%[SeriesID: SCH-does-not-exist]%' clause is present in the generated SQL at all.

Hypothesis (A) is far more likely given the magnitude (299 rows, 10 series — consistent with "almost all Pending tasks", not a subtly-wrong-but-still-narrow filter) and given this checkout is explicitly known to differ from the deployed build.

4. Required Fix

  • Redeploy from (or diff against) this repo's current backend/src/pm-tasks.controller.ts updateSchedule()/applyScheduleUpdatesToTasks() — confirm the deployed build actually contains the scheduleId/description contains scoping shown above.
  • Add a defensive guard regardless of root cause: if the resolved task list's length is implausibly large (e.g. more than some sane per-series ceiling) or if tasks.some(t => t.scheduleId !== seriesId) for the exact-scheduleId path, throw instead of proceeding — never trust an updateMany/loop-update to have been correctly scoped without verifying the resulting set first.
  • Add an integration test (see backend/test/live-user-journeys.e2e-spec.ts, Journey 3 — the dangerous assertion was deliberately removed from the automated suite here to avoid repeatedly damaging the shared dev DB; re-add it once fixed, against a disposable DB only) asserting that an unknown seriesId returns [] and touches zero rows.
  • Consider adding an audit log entry for schedule/series bulk updates (currently assignedTo changes on PmTask are not logged at all via CmmsService.logAction()), so an incident like this is traceable and reversible in the future.

5. Data Recovery

No application-side recovery is possible. assignedTo changes are not audit-logged, so the pre-incident assignee for each of the 299 affected tasks cannot be reconstructed from the API.

Options for whoever owns the dev DB:

  • Restore cmms_pm_tasks (or the whole DB) from a backup/snapshot taken before 2026-08-26 02:46 UTC, if one exists.
  • If no backup exists, the 10 affected series listed in §1 will need their assignees manually re-set by whoever owns each series (their engineer/manager) — treat the current assignedTo = TECH-TST-1 on those rows as unreliable.
