Nightly PM Task Duplication Priority 1

Confirmed live on http://10.144.15.76:3000 on 2026-09-21 by querying GET /pm-tasks directly. A nightly job is inserting a fresh batch of future task occurrences for every active PM schedule without checking what already exists \u2014 the table grows unbounded, forever, for every user.
Must be fixed before prod release. This is not cosmetic \u2014 the PM task table is growing by ~270 rows/day system-wide right now and has been for weeks. Left running in prod this will cause unbounded DB growth and endless duplicate future tasks visible to every technician/engineer.

This rules out an idempotent "sync to N future occurrences" job \u2014 it is blindly appending a brand-new future horizon on top of the existing one every night rather than checking/reconciling against tasks that already exist for that schedule.

2. Impact

  • Unbounded row growth in the PM task table \u2014 currently ~270 rows/day across all schedules combined, compounding daily.
  • Users see an ever-growing list of duplicate future "Pending" tasks for the same asset/frequency that never get cleaned up.
  • Reporting/exports (e.g. PM Report PDF) and dashboards that iterate all tasks for an asset will only get slower and less accurate as duplicate placeholder rows accumulate.

3. Likely root cause (for backend team to confirm)

Whatever job/cron generates upcoming occurrences for each PMSchedule (likely intended to maintain a rolling N-occurrence or N-week horizon per schedule) is not checking for already-generated future tasks before inserting new ones. Expected behavior: on each run, compute the set of occurrences that should exist going forward and only insert the ones missing (upsert/reconcile by scheduleId + nextDueDate, or track a "generated through" watermark on the schedule). Actual behavior: it inserts a full new horizon unconditionally every run.

4. Requested fix

  1. Before inserting new occurrences for a scheduleId, check existing non-cancelled tasks for that schedule and skip/no-op if the schedule is already generated through the target horizon.
  2. One-time cleanup of the duplicate rows already created by this bug (all creators above, plus any others affected) \u2014 needs backend/DB team judgment on which duplicate rows are safe to remove (keep the earliest occurrence per due date per schedule, drop the rest that are still Pending and duplicate a due date already covered).
  3. Add a regression check (or alert) that flags if a schedule's task count grows without a corresponding increase in distinct nextDueDate values.
