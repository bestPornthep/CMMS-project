Real Checklist Photo Capture — Backend Requirements

Checklist "Require Photo" is now a real, camera-only capture on the frontend instead of a mock button. Backend upload storage is not yet implemented — this documents the target design.
  • 1. What changed on the frontend (already shipped)
  • 2. Interim behavior — one required backend prerequisite
  • 3. Deferred: dedicated upload endpoint POST /api/v1/pm-tasks/:id/checklist/:index/photo
  • 4. Implementation Notes / Edge Cases

1. What changed on the frontend (already shipped)

Technicians can no longer fake photo evidence with a single click. The "Upload" button in pm-record.component.html was replaced with a hidden <input type="file" accept="image/*" capture="environment"> triggered by a "Take Photo" button.

  • capture="environment" opens the device's rear camera app directly on Android Chrome and iOS Safari — no gallery/file picker step — which satisfies the requirement to prevent reusing old photos.
  • True live in-app camera view (getUserMedia) was considered but rejected for now: it requires a secure context (HTTPS or localhost), and the app currently runs over plain HTTP on a LAN IP (environment.ts → http://10.144.15.76:3000). Revisit if/when the site is served over HTTPS.
  • Captured photos are resized (max 1280px side) and re-encoded as JPEG client-side (compressImageToDataUrl() in pm-record.component.ts) before being stored, to keep payload size reasonable.
  • A "Retake" button lets the technician replace a captured photo before submitting.

2. Interim behavior — one required backend prerequisite

The compressed photo is stored as a base64 data:image/jpeg;base64,... string directly in the existing checklist[].photoUrl field — the same string field the old mock path (assets/demo-photo.jpg) used. This round-trips through the existing PUT /api/v1/pm-tasks/:id endpoint unchanged code-wise, since that route's handler (pm-tasks.controller.ts → update()) takes @Body() body: any with no DTO/whitelist validation.

But this will 413 today. main.ts calls NestFactory.create(AppModule) with no body-parser options, so Nest/Express fall back to the default JSON body size limit of 100kb. A single compressed photo (JPEG, max 1280px side, quality 0.7) typically lands in the 100–300KB range before base64 encoding adds another ~33% — i.e. a normal checklist photo will routinely exceed 100kb and Express will reject the whole PUT request with 413 Payload Too Large before it even reaches the controller. A checklist with 2–3 required photos makes this a near-certainty, not an edge case.

Required one-line fix

// main.ts, after NestFactory.create():
app.useBodyParser('json', { limit: '10mb' });
app.useBodyParser('urlencoded', { limit: '10mb', extended: true });

This is the only backend change required for real photo capture to function end-to-end against a live server. Everything else in this section (route, DTO, permissions) is already correct as-is.

3. Deferred: dedicated upload endpoint POST /api/v1/pm-tasks/:id/checklist/:index/photo POST

Storing many full photos as base64 inside the checklist JSON column doesn't scale well (each photo inflates the column ~33% over raw bytes, and every task update re-sends every photo already on the record). When there's backend bandwidth, replace inline base64 with a real file upload:

Proposed request

POST /api/v1/pm-tasks/:id/checklist/:index/photo
Content-Type: multipart/form-data
Body: photo=<file>

Proposed handler sketch

@Post(':id/checklist/:index/photo')
@UseInterceptors(FileInterceptor('photo', {
  storage: diskStorage({
    destination: './uploads/pm-checklist-photos',
    filename: (req, file, cb) => cb(null, `${req.params.id}-${req.params.index}-${Date.now()}.jpg`),
  }),
  limits: { fileSize: 5 * 1024 * 1024 }, // 5MB
  fileFilter: (req, file, cb) => cb(null, /^image\/(jpe?g|png|webp)$/.test(file.mimetype)),
}))
async uploadChecklistPhoto(@Param('id') id: string, @Param('index') index: string, @UploadedFile() file: Express.Multer.File, @CurrentUser() user: any) {
  // same permission checks as update() (isOwner / canRecord), then:
  // 1. load task, parse checklist JSON
  // 2. set checklist[index].photoUrl = `/uploads/pm-checklist-photos/${file.filename}`
  // 3. persist checklist back to the task row
  // 4. return { photoUrl }
}

multer is already a backend dependency (see package.json) but currently unused anywhere in backend/src — this would be its first wiring. Serve the uploads/ folder as static assets via app.useStaticAssets() in main.ts so the returned photoUrl is directly usable as an <img src>, same as today.

Auth: apply the same permission logic as update() in pm-tasks.controller.ts (owner/assignee/delegation checks) before accepting an upload for a task — don't let this become an unauthenticated file-drop endpoint.

4. Implementation Notes / Edge Cases

  • Backward compatible: photoUrl stays a plain string either way (base64 data URL today, disk-relative URL later) — no schema change, no frontend change needed when this ships beyond swapping which value populates photoUrl.
  • Migration: existing base64 photos already saved on historical tasks don't need to be migrated — they'll keep rendering fine as <img> src values indefinitely.
  • Storage growth: disk-based storage needs a retention/cleanup policy decision (not addressed here) since photos currently have no expiry.
  • HTTPS: unrelated to this endpoint (multipart upload works fine over plain HTTP) — only the alternative live in-app camera view (§1) needs HTTPS.
