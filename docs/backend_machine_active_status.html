Machine Active/Inactive Status + Cascade to PM Plans

New frontend page (frontend/src/app/pages/pm-machines/) lets users add machines and deactivate ones no longer in use. This requires new backend fields + one new endpoint that don't exist yet.

1. New fields

EntityFieldTypeDefaultNotes
AssetisActivebooleantrueSame convention as the existing User.isActive \u2014 absent/undefined is treated as true for back-compat with existing rows.
AssetworkCenterstring, nullablenullNew required-in-UI field — factory work center code for the machine (e.g. WC-01). Not yet accepted/returned by the backend; frontend form requires it, so existing rows will show blank until backend support lands.
PMScheduleisActivebooleantruefalse = paused, the scheduler must not generate any new occurrences for it.
PMTask.statusnew enum value Cancelled——Added alongside existing Pending / In Progress / Pending Approval / Done / Overdue.
PMTaskcancelledReason, cancelledAtstring / datetime, nullablenullSet only when a task is auto-cancelled by the cascade below.

GET /assets must return isActive and workCenter on every row. POST /assets must accept workCenter in the create body.

2. New endpoint PATCH /assets/:id

Body: { name?: string, department?: string, location?: string, workCenter?: string, isActive?: boolean }. Same permission gate as asset creation today (pm.create.submit).

PATCH /api/v1/assets/CNC-014
{ "isActive": false }

Cascade on isActive: true → false (deactivate)

In one transaction:

  1. Set Asset.isActive = false.
  2. Set isActive = false on every PMSchedule where assetId matches (stops future generation).
  3. For every PMTask where assetId matches and status is one of Pending, In Progress, Pending Approval, Overdue: set status = 'Cancelled', cancelledReason = 'Machine deactivated', cancelledAt = now().
Do not touch Done tasks. Completed PM history must never be modified or deleted \u2014 it's relied on for audit/trace-back.

Cascade on isActive: false → true (reactivate)

  1. Set Asset.isActive = true.
  2. Set isActive = true on every PMSchedule where assetId matches (resumes future generation from the schedule's own cadence).
  3. Do not touch previously-Cancelled tasks \u2014 they remain Cancelled permanently, as history of the period the machine was inactive.

Editing name/department/location

Plain field update, no cascade. Machine id itself is immutable (not part of this endpoint's body).

3. Audit log

Each create / edit / deactivate / reactivate should write an AuditLog row, consistent with existing actions elsewhere in the app (e.g. "Machine Deactivated", "Machine Reactivated", "Machine Updated", target = the asset).

4. Frontend status

Frontend (pm.service.ts updateAsset()) is already built against this exact contract and additionally mirrors the cascade locally (client-side) right after a successful call, purely for immediate UI feedback \u2014 the backend cascade above is the source of truth. Until this ships, the Machines page has a dev-only "mock data" toggle (!environment.production) that exercises the full create/deactivate/reactivate flow without calling the backend at all, so the UI can be tested independently of backend readiness.
