Profile Config (User Management) — Backend Requirements

New admin-only page: create user accounts and grant permissions. Frontend is fully built against these contracts — this doc lists what the backend still needs to implement.
  • 1. Concept — every user starts as a Technician
  • 2. New Endpoint: POST /api/v1/users
  • 3. Changed Endpoint: PATCH /api/v1/users/:id (add isActive)
  • 4. Changed Endpoint: GET /api/v1/users (return isActive)
  • 5. Schema Change (new column)
  • 6. Login must reject inactive users
  • 7. Permission Catalog (reference)
  • 8. Implementation Notes / Edge Cases

1. Concept

Admin creates a new employee account. Every new account is created as a plain technician with the standard technician permission set. The admin then picks a Role Template (Technician / Engineer / Manager / Admin) in the same form — this sets baseRole and auto-grants that role's standard permission set. Admin can also check a few extra permissions on top of the standard set (e.g. an Engineer with an extra permission, given the free-text roleLabel "Senior Engineer" for display purposes).

No new role-level concept is introduced — still exactly the 4 existing baseRole values (technician/engineer/manager/admin). "Senior Engineer" etc. is just a roleLabel string, not a new enum value. Nothing changes about how AuthService.hasPermission() already interprets baseRole and permissions — see existing backend/src/users.controller.ts and frontend auth.service.ts.

2. New Endpoint: POST /api/v1/users POST

File: backend/src/users.controller.ts. Does not exist yet — only GET/GET :id/PATCH :id exist today. Admin only (same guard pattern already used in update(): if (actor.baseRole !== 'admin') throw new ForbiddenException()).

Request body

{
  "employeeId": "TECH-FAC-5",
  "name": "Somchai Jaidee",
  "initials": "SJ",
  "baseRole": "technician",       // 'technician' | 'engineer' | 'manager' | 'admin'
  "roleLabel": "Technician",      // free text, admin-editable display label
  "department": "Facility",       // one of Facility/Mechanic/Manufacturing/Maintenance/Test/All
  "password": "plaintext-from-form",
  "ownedProducts": [],            // string[] of product IDs, or ["*"] for all
  "permissions": [ "pm.dashboard.view", "pm.record.view", "pm.record.submit", "pm.calendar.view" ]
}

Handler logic

if (actor.baseRole !== 'admin') throw new ForbiddenException('Admin only');

if (!body.employeeId || !body.name || !body.password) {
  throw new BadRequestException('employeeId, name, and password are required');
}

const existing = await prisma.user.findUnique({ where: { employeeId: body.employeeId } });
if (existing) {
  throw new ConflictException(`User ${body.employeeId} already exists`);
}

const passwordHash = await bcrypt.hash(body.password, 10);

const created = await prisma.user.create({
  data: {
    employeeId: body.employeeId,
    name: body.name,
    initials: body.initials,
    passwordHash,
    baseRole: body.baseRole,
    roleLabel: body.roleLabel,
    department: body.department,
    permissions: JSON.stringify(body.permissions || []),
    isActive: true, // see schema change below
  },
});

if (body.ownedProducts?.length) {
  for (const p of body.ownedProducts) {
    await prisma.userOwnedProduct.create({ data: { employeeId: created.employeeId, productId: p } });
  }
}

await cmms.logAction(
  `Created user ${created.employeeId} (${created.roleLabel})`,
  { id: actor.employeeId, name: actor.name },
  { id: created.employeeId, name: created.name, isUser: true },
  'N/A', 'security', created.department,
);

return this.getOne(created.employeeId); // reuse existing getOne() to shape the response consistently

Pseudocode — adapt to existing style/helpers already in users.controller.ts. Response shape should match the existing GET /users/:id response (same fields the frontend User model already expects).

3. Changed Endpoint: PATCH /api/v1/users/:id PATCH

Already exists and already admin-gated. Just needs one more field accepted in the body handling in update():

if (body.isActive !== undefined) data.isActive = body.isActive;

This is what powers the frontend's Deactivate / Reactivate button on the Profile Config user list — it currently calls this same endpoint with { isActive: false } / { isActive: true }.

4. Changed Endpoint: GET /api/v1/users / GET /api/v1/users/:id GET

Both already exist. Just add isActive: u.isActive to the returned object in both getAll() and getOne() so the frontend list can show the Active/Inactive badge. No filtering needed — return all users regardless of isActive so admin can see and reactivate deactivated accounts from the same list.

5. Schema Change (new column)

Add to User in backend/prisma/schema.prisma:

isActive  Boolean  @default(true) @map("is_active")

Migration: ALTER TABLE cmms_users ADD is_active BIT NOT NULL DEFAULT 1; — additive, backward compatible, all existing rows default to active. Follow the existing convention in backend/prisma/manual-sql/ for a standalone script (e.g. add-user-is-active.sql) alongside the schema.prisma edit.

6. Login must reject inactive users

File: backend/src/auth/auth.service.ts, login(). Add a check right after the user is found (before password comparison, so a deactivated account's password isn't even validated):

if (!user.isActive) {
  throw new UnauthorizedException('This account has been deactivated');
}

Deactivating is a soft-delete — no rows or FK references (audit logs, PM tasks assigned to this employeeId, delegations) are removed. This preserves audit history integrity, consistent with why the frontend button is labeled "Deactivate", not "Delete".

8. Implementation Notes / Edge Cases

  • New permission string used by the route guard: pm.users.manage. This is frontend-only (checked client-side in AuthService.hasPermission(), hardcoded to baseRole === 'admin') — it does not need to exist in any backend permission list or be persisted anywhere. Flagging it only so it isn't mistaken for a missing/broken permission if it's grepped for on the backend.
  • Employee ID uniqueness — POST /users must 409 on a duplicate employeeId (the frontend does not pre-check this before submitting).
  • Password hashing — reuse the same bcrypt.hash(password, 10) pattern already used in the existing PATCH /users/:id handler.
  • Owned products replace, not merge — on both create and update, treat the incoming ownedProducts array as the full replacement set, same as the existing PATCH handler already does (delete-all-then-recreate).
  • No endpoint to hard-delete a user — intentionally not requested. Deactivate (isActive: false) is the only removal path, to preserve audit/PM history referential integrity.
