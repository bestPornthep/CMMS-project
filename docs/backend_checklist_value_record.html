Checklist "Require Value" — Backend Requirements

New checklist item flag: technician must type a free-text value (e.g. a reading) before submitting. Frontend is fully implemented; one small backend DTO gap remains.
  • 1. What changed on the frontend (already shipped)
  • 2. The one backend gap: POST /api/v1/pm-tasks
  • 3. Everything else needs no backend change

1. What changed on the frontend (already shipped)

Checklist items now support an independent requiresValue flag alongside the existing requiresPhoto flag, configurable in both the Template builder and PM Create's checklist editor. When set, the technician sees a free-text input in PM Record and must fill it in (stored as checklist[].value) before the record can be submitted — enforced client-side same as the existing missing-photo check. Recorded values also render in the PM Reports export grid in place of the "√" mark.

No range/type validation — plain free text, by design (technician may need to write "N/A" or a note instead of a strict number).

2. The one backend gap: POST /api/v1/pm-tasks

File: backend/src/dto/create-pm-task.dto.ts. This is the only endpoint in the checklist's path that validates against a strict, whitelisted DTO (global ValidationPipe({ whitelist: true }) in main.ts strips any property not declared on the DTO class). ChecklistItemDto currently only declares text and requiresPhoto:

class ChecklistItemDto {
  @IsString() @IsNotEmpty() text: string;
  @IsOptional() @IsBoolean() requiresPhoto?: boolean;
  // requiresValue is silently stripped here today
}

Without adding the field below, creating a one-time PM task (not a recurring schedule) whose checklist has a requiresValue: true item will silently lose that flag on save.

Required change

class ChecklistItemDto {
  @IsString() @IsNotEmpty() text: string;
  @IsOptional() @IsBoolean() requiresPhoto?: boolean;
  @IsOptional() @IsBoolean() requiresValue?: boolean;  // add this
}

3. Everything else needs no backend change

  • POST /api/v1/pm-tasks/schedule (recurring) and POST /api/v1/templates both take @Body() body: any with no DTO — arbitrary checklist item shapes already pass through untouched.
  • PUT /api/v1/pm-tasks/:id (technician record submission, storing done/value/photoUrl) also takes @Body() body: any — no change needed there either.
  • No schema change — checklist is stored as a JSON string column already.
