Note: Overdue is only ever reached from Pending (never from In Progress) — see §9. A task that is already assigned and running late stays In Progress; there's no "overdue while in progress" state today.

2. Create — single task vs recurring series

Frontend guard (pm-create.component.ts)

  • Blocks submit unless productId, department, assetId, pmType are all set (custom frequency also needs customDurationValue > 0).
  • Empty checklist only warns — doesn't block.
  • Hard error if the selected asset's location/department don't match the chosen product/department.
  • Product/asset picker is scoped by pm.create.submit accessible products (getAccessibleProducts).

Backend (pm-tasks.controller.ts)

  • create() — admin/manager/engineer always allowed; otherwise requires a delegation with pm.create.submit for that product. Re-validates asset existence + location/department match server-side (400 if mismatched) — not just trusting the frontend.
  • createSchedule() (POST schedule) — same permission rule, then:
    1. Generates seriesId = SCH-<timestamp>-<rand>.
    2. calculateDates(frequency) → up to 365 future dates, capped at 1 year ahead.
    3. Creates one persistent PmSchedule row (the series "definition") and one PmTask row per date, each tagged description: "[SeriesID: <id>]\n..." and scheduleId: seriesId.
Why both a PmSchedule row and a text marker? The PmSchedule row lets the nightly topUpSchedules() cron keep generating future tasks indefinitely. The [SeriesID: xxx] text marker in description is legacy, kept because the frontend (pm-assign, pm-calendar, global search) still parses it to group series in the UI. Both must stay in sync — a code comment in pm-tasks.controller.ts right above createSchedule() explains a prior bug where only the marker existed and the cron couldn't see frontend-created series at all.

Task ID generation (cmms.service.ts createTaskWithRetry())

const deptPrefix = department.substring(0, 3).toUpperCase();
const taskId = `PM-${deptPrefix}-${(maxNum + 1).toString().padStart(4, '0')}`;

Runs in a Serializable transaction, scans existing IDs with that prefix, takes max numeric suffix + 1. Retries up to 5× on unique-constraint (P2002) or serialization-failure (P2034) errors — handles concurrent creates racing for the same next number.

3. Unassigned tab — series representative logic

pendingTasks computed in pm-assign.component.ts: filters status === 'Pending' + canManageTask() + department filter, sorts ascending by nextDueDate first, then dedupes by [SeriesID: x] — first one seen (i.e. the soonest-due occurrence) wins as the representative row.

Rule: Unassigned tab representative = earliest due date. Makes sense here — it's literally "the next occurrence you need to assign."

4. Assign action

assignTask() / confirmBulkAssign() in pm-assign.component.ts:

  • Re-checks canManageTask() and a Product-Asset mismatch guard (asset's location must equal task's productId) before allowing the click to do anything.
  • Series-aware: even if the clicked/selected row isn't the earliest-due occurrence, the code looks up the actual earliest-due Pending task sharing the same seriesId and assigns that one — you can never accidentally assign a later occurrence out of order.
  • Sets in one update: status: 'In Progress', assignedTo, assignedAt: new Date(), assignedBy: currentUser.

canManageTask(): admin/manager always; engineer needs product ownership (and is blocked from another engineer's owned/created task); technician needs pm.assign.submit delegation + same department.

5. Assigned tab — series representative logic (different rule!)

assignedTasks computed: filters status !== 'Pending' + canManageTask(), groups by seriesId, but the representative is the task with the most recent assignedAt — not earliest due date.

Why the two tabs use different rules (verified intentional, fixed last session): if Unassigned-style "earliest due" were used here too, a brand-new assignment on a later occurrence could be hidden behind an older, still-outstanding occurrence in the same series (e.g. one still In Progress/Pending Approval) — looking like the assign silently failed. Display sort (by nextDueDate ascending) is unchanged; only which row represents the group differs from the Unassigned tab.

6. Technician records work

pm-record.component.ts — technician sees tasks with status ∈ {Pending, In Progress, Overdue} and assignedTo === self (deduped by series, same earliest-due-representative pattern as pm-assign's Unassigned tab).

submitRecord() (non-approver branch) validates before allowing submit:

  • Every checklist item must be checked (allChecked).
  • Any item with requiresPhoto: true must have a photoUrl.
  • actualHours must be > 0, finite, and <= 999.

On success: In Progress → Pending Approval, sets completedAt, completedBy, actualHours; appends a [Tech|<timestamp>]: ... block to recordNotes (replacing any prior Tech block, but keeping Approver/Rejected history blocks).

7. Approve / Reject

Same component, same selectedTask/submitRecord() flow — no separate approve/reject component exists; it branches on isApprover (engineer | manager | admin).

Status-transition guard (only applies when non-approvers act):

TECHNICIAN_ALLOWED = {
  'Pending':          ['In Progress'],
  'In Progress':      ['Pending Approval'],
  'Pending Approval': [],   // technicians can't approve/revert
}

Approvers bypass this map entirely but are blocked from any change once existing.status === 'Done' — only when the request body includes status (see gap in §11). approvedBy/approvedAt/rejectedBy/rejectedAt are silently dropped from the write unless the requester isApprover, even if a non-approver's body includes them.

9. Scheduler jobs

JobCadenceWhat it does
markOverdueTasks()HourlyUPDATE ... WHERE status='Pending' AND nextDueDate < now SET status='Overdue'. Only unassigned (Pending) tasks are affected — a running In Progress task never becomes Overdue.
topUpSchedules()Nightly (midnight)For every PmSchedule row (no active/inactive flag — all rows are eligible), finds the latest Pending task for that schedule, generates further dates via calculateDates(frequency, startDate), skips any exact-duplicate date, creates new PmTask rows — maintains a rolling ~1-year buffer per series indefinitely.

10. Visibility quirks (Done tasks, Calendar bucketing)

  • pm.service.ts loadData() excludes Done tasks on initial app load (excludeStatus='Done'). Only loadHistoricalTasks() backfills them, and it's called only from pm-record.component.ts and pm-reports.component.ts — pm-calendar.component.ts never calls it, so a fresh page load landing directly on /pm-calendar won't show Done tasks until the user has visited Record PM or PM Reports at least once that session.
  • pm-calendar.component.ts buildDay() buckets a Done task by completedAt (when the work actually happened), not nextDueDate — intentional, but a Done task's chip can appear to "move" to a different day than its original due date.

11. Gaps found during this review

Done-task guard only fires when the request includes status. A PUT to an already-Done task that omits status but changes other fields (e.g. assignedTo, recordNotes) is not currently blocked by any guard. This is exactly the gap the Reassign feature's backend design closes (see docs/backend_pm_reassign_api.html §2 Rule A) — flagging it here again so it's visible in the full lifecycle context, not just the reassign-specific doc.
Overdue has no entry in TECHNICIAN_ALLOWED. A technician's own request to move an Overdue task to In Progress would be rejected by that map (falls back to an empty allowed-list). In practice this likely isn't hit because assignment is normally done by an engineer/manager/admin (all isApprover, exempt from the map) — but no end-to-end trace confirms a technician can self-transition an Overdue task today. Not fixing as part of this review; noting for awareness.
