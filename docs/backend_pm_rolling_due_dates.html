Rolling Due Dates on Approval — Backend Requirements

Independent feature — not related to Reassign (see separate backend_pm_reassign_api.html). Triggered by the existing Approve action, every time, forever.

  • 2. Where this hooks in

  • 4. Shared date-math helper

1. Business Rule

Every time a task in a recurring series is approved (Pending Approval → Done, approvedAt set), recalculate the due dates of every remaining Pending occurrence in that same series, anchored off the actual approval date instead of the original fixed calendar dates generated at series-creation time.

nextDueDate is an expected date, not a hard deadline — the same recalculation applies whether the task was approved before or after its original due date. No special-casing for "early" vs "late."

Rejecting a task does not trigger this — no approvedAt is set on reject, so nothing recalculates.

2. Where this hooks in

File: backend/src/pm-tasks.controller.ts, update() — the existing generic PUT /api/v1/pm-tasks/:id handler already used for Approve (an isApprover setting status: 'Done', approvedBy, approvedAt). Add this as a side effect after that update succeeds, only when:

const isApproving = body.status === 'Done' && body.approvedAt !== undefined && existing.status !== 'Done';

Do not add a new endpoint for this — unlike Reassign, this isn't a distinct user-triggered action, it's a side effect of the Approve flow that already exists.

3. Algorithm

if (isApproving) {
  const seriesWhere = existing.scheduleId
    ? { scheduleId: existing.scheduleId, status: 'Pending' }
    : extractSeriesIdFromDescription(existing.description)
      ? { description: { contains: `[SeriesID: ${seriesId}]` }, status: 'Pending' }
      : null;

  if (seriesWhere) {
    const pendingSiblings = await prisma.pmTask.findMany({
      where: seriesWhere,
      orderBy: { nextDueDate: 'asc' },
    });

    const newDates = calculateDatesFromAnchor(existing.frequency, updated.approvedAt, pendingSiblings.length);
    // newDates[0] = approvedAt + 1x frequency, newDates[1] = approvedAt + 2x frequency, ...

    await prisma.$transaction(
      pendingSiblings.map((sibling, i) =>
        prisma.pmTask.update({ where: { id: sibling.id }, data: { nextDueDate: newDates[i] } })
      )
    );
  }
}

Ordering: siblings sorted by their current nextDueDate ascending (1st-in-line, 2nd-in-line, ...) — that relative order is preserved, only the absolute dates change.

4. Shared date-math helper

CmmsService.calculateDates() (backend/src/cmms.service.ts) already contains the per-frequency date-increment logic (addFunc for Daily/Weekly/Monthly/Quarterly/Yearly/custom "N unit(s)"). Extract that increment logic into a small reusable helper so both the original bulk-generation path and this new recalculation path share the exact same frequency parsing — don't duplicate it:

private getFrequencyIncrementFn(frequency: string): (d: Date) => void { /* existing addFunc logic, extracted */ }

calculateDatesFromAnchor(frequency: string, anchor: Date, count: number): Date[] {
  const addFunc = this.getFrequencyIncrementFn(frequency);
  const dates: Date[] = [];
  let current = new Date(anchor);
  for (let i = 0; i < count; i++) {
    addFunc(current);
    dates.push(new Date(current));
  }
  return dates;
}

5. Implementation Notes / Edge Cases

  • Already-Done occurrences are never touched — only status='Pending' siblings get new dates, consistent with every other rule in this feature set (approved history is immutable).
  • Repeats on every approval, indefinitely — each new approval re-recalculates all currently-Pending siblings again from the latest approvedAt, overwriting whatever dates resulted from the previous recalculation. This is intentional — the schedule continuously re-anchors to actual approval timing.
  • topUpSchedules() needs no change — it already anchors new future-generated dates off "the latest Pending task's nextDueDate" (scheduler.service.ts), which will already reflect this recalculation.
  • Legacy series without a PmSchedule row — same fallback pattern as Reassign: match by scheduleId when present, else by the [SeriesID: xxx] description marker.
  • Standalone (non-series) task — seriesWhere is null, nothing to recalculate, approve behaves exactly as it does today.
  • Interaction with Reassign: these two features are independent and can both touch the same series' Pending siblings, just via different triggers (Approve vs the dedicated Reassign endpoint) — no shared code path, no ordering dependency between them.
