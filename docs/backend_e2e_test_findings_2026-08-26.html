Findings

1. Recurring schedule update with an unmatched seriesId mass-reassigns unrelated tasks Critical Fix drafted, needs deploy

This already happened — 299 real tasks across 10 unrelated series were reassigned during testing. Full incident report, root cause, and required fix: docs/backend_pm_schedule_reassign_bug.html.

2. Technicians can delete PM Templates in their own department Medium — permission gap Fixed locally

Confirmed live: a technician calling DELETE /api/v1/templates/:id (or the name+department variant) on a template in their own department gets 204 instead of 403. Template creation already correctly forbids technicians — deletion didn't have the matching role check, only a department check.

Fix applied in this checkout: backend/src/templates.controller.ts, both delete() and deleteByNameAndDept() now also require admin/manager/engineer before the department check.

3. Editing a completed ("Done") PM task still succeeds if the request omits status Medium — data integrity Fixed locally

Confirmed live: PUT /api/v1/pm-tasks/:id with { "recordNotes": "..." } (no status field) on an already-Done task returns 200 and applies the edit. The existing "cannot modify a completed task" guard only fired when status was present in the body.

Fix applied in this checkout: backend/src/pm-tasks.controller.ts update() now checks existing.status === 'Done' unconditionally, before looking at body.status.

4. PATCH /api/v1/users/:id on an unknown id returns 500 instead of 404 Low Fixed locally

Confirmed live: patching a nonexistent employeeId returns an unhandled 500 (Prisma "record not found" error), unlike every other resource controller in this API which explicitly checks existence and throws 404.

Fix applied in this checkout: backend/src/users.controller.ts update() now does a findUnique existence check first.

5. Recurring schedule startDate not honored Medium Fixed locally

Already documented in docs/backend_pm_create_start_date.html. Fix applied in this checkout per that doc's spec (no schema change needed) — createSchedule() now uses body.startDate as task #1's exact due date when provided, rejecting past dates.
