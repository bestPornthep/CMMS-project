1. Nightly PM Task Duplication P1

Must be fixed before prod. Confirmed live on http://10.144.15.76:3000 on 2026-09-21 via GET /pm-tasks. A nightly job inserts a new batch of future occurrences for every active schedule without checking what already exists. Table growth is ~270 rows/day system-wide and unbounded.

Evidence

Created byTotal tasksSchedulesNew rows / night
ENG-TST-16,03114up to 52 per schedule, nightly since 2026-08-12 (37 nights)
MGR0014731+11/night since 2026-09-14
ENG-FAC-14191+52/night since 2026-09-14
ENG-MEC-11802same pattern
System-wide7,108—~270/day, still growing

Worst schedule: SCH-1786510329530-890 (Weekly, ENG-TST-1) has 1,924 rows. Exactly 52 new rows per night, zero gaps. The 52 nextDueDate values created 2026-08-12 and the 52 created 2026-08-13 have 0 overlap, so this is a blind append of a fresh horizon, not an idempotent sync.

Impact

  • Unbounded DB growth.
  • Ever-growing duplicate future Pending tasks per asset/frequency.
  • Slower, less accurate reports/exports/dashboards.

Likely root cause (backend to confirm)

The generator (rolling N-occurrence horizon per PMSchedule) does not check existing future tasks before inserting.

Requested fix

  1. Before inserting for a scheduleId, check existing tasks (any status, including Cancelled). Only insert a due date that has no row at all.
  2. One-time cleanup of existing duplicates. Keep the earliest row per due date per schedule, drop still-Pending duplicates. Needs DB-team judgment.
  3. Regression check/alert: task count growing without a matching rise in distinct nextDueDate.
Do not exclude Cancelled from the "already generated" check. The frontend lets an engineer cancel a task occurrence directly (PmService.cancelPmTaskSeries(), no approval). That cancels not-yet-done future occurrences in the series and leaves PMSchedule.isActive untouched. If the generator treats a Cancelled row as "missing" and inserts a fresh Pending row for the same scheduleId + nextDueDate, the next nightly run silently undoes the cancel.

Repro (read-only, via API)

-> group by scheduleId, then each schedule's rows by createdAt date

2. Duplicate PM Type Hard Block Ready

An asset may only ever have one PM per frequency (any status, even Done). Must be enforced server-side. The frontend check is best-effort and not race-safe.

EndpointsPOST /pm-tasks/schedule, POST /pm-tasks
RequirementDB-level UNIQUE(assetId, normalizedFrequency). Not check-then-insert.
On conflict409 Conflict with the conflicting task's id/status/assignee. Catch the DB conflict and translate it.
GotchaCustom durations equal to a preset (1 month(s) = Monthly) must collide. Normalize with the same alias table + lowercase/trim as the frontend.
Race safetyTwo users submitting the same asset+frequency at once must not both succeed. Only the unique constraint guarantees that.

6. PM Task ID Format Backend todo

Replaces PM-XXX-0001 (CmmsService.generateTaskId()) with an ID that embeds machine and period, with a sequence that stays valid for 10+ years.

PM- {MachineID}- {PeriodCode}- {Seq}

Example: PM-FCT-RN005-AR-A-001-1m-01, next ...-1m-02, 13th ...-1m-13.

Period codes (from PMSchedule.frequency)

FrequencyCodeFrequencyCode
Daily1dCustom N Hour(s){N}h
Weekly1wCustom N Day(s){N}d
Monthly1mCustom N Week(s){N}w
Quarterly3mCustom N Month(s){N}m
Yearly1yCustom N Year(s){N}y
Reuse the FREQUENCY_ALIASES normalization from pm.service.ts so "3 month(s)" and Quarterly get the same code.

Sequence rules

  1. One counter per (assetId, periodCode).
  2. Starts at 1, String(n).padStart(2,'0'). Minimum width 2, never truncated (1→01, 100→100, 4380→4380). No fixed digit count in code.
  3. Never resets: not per year, not on deactivate/reactivate (paused at 12, resumes at 13).
  4. Increments only when an occurrence is actually generated. Never pre-reserved in bulk.
FrequencyPer yearAfter 10 yearsDigits
Monthly12120up to 3
Weekly52520up to 3
Daily3653,650up to 4
Custom 4h~2,19021,900up to 5

Counter storage and concurrency

cmms_pm_id_sequences
  assetId     varchar  (FK -> cmms_assets.id)
  periodCode  varchar
  lastSeq     int      default 0
  PRIMARY KEY (assetId, periodCode)

UPDATE cmms_pm_id_sequences
SET lastSeq = lastSeq + 1
OUTPUT INSERTED.lastSeq
WHERE assetId = @assetId AND periodCode = @periodCode;
-- no row matched -> INSERT (assetId, periodCode, lastSeq=1), use 1
Must be atomic, in the same transaction that creates the task. Never read-then-write. A non-atomic counter under concurrent nightly + manual create hands out duplicate numbers. Fix #1 with the same transactional discipline.
No migration. All current PM task rows on the dev DB are mock data (confirmed with user). Start minting the new format for new tasks. Truncating cmms_pm_tasks + the new sequence table is fine for a clean dev slate.

Frontend: no change. IDs are server-assigned (create sends id: '') and displayed as returned, so the new format appears everywhere (lists, PDFs, audit log).

Rules the frontend already follows

RuleDetail
Net state, not a logA pending card is the merged desired end-state for one machine (ProposedMasterPlanState). Re-submitting merges into the existing card and appends a history entry. If the merge reduces to "no change", the card is dropped.
Reconcile, never replayOn approve, diff proposedState against current asset/schedule state and apply only the delta.
IdempotentApproving an already-resolved id is a no-op error (Already resolved). Two approvers racing must not double-apply.
One revision per batchBulk approve reserves one version label (A, B, C…) up front and saves one snapshot at the end. Also one shared batchTime for audit rows.
Empty diffResolved as approved, but no audit row and no snapshot.
RejectReason required (non-blank).
PermissionsSubmit: canProposeMasterPlanChange(). Approve/reject: pm.masterplan.approve (manager/admin only). The Approvals page and sidebar link are gated on the same permission.

Send to Master Plan (new machines)

Status. Frontend-derived proposal, not agreed with backend. The startup rule that decides which machines begin "In plan" is a demo seed (a machine with any open task counts as in plan), not a real rule.
ItemProposal
Plan status per machineAdd a plan-status field on the asset (frontend: isInMasterPlan). A new machine starts Not in plan. Not-in-plan machines are edited directly (no approval) and generate no real PM tasks.
Draft PM typesCreate PM on a Not-in-plan machine saves a draft instead of an approval request. Store drafts server-side per asset: assetId, frequency, title, description?, estimatedHours?, partsRequired?, checklist?, startDate?, isRecurring?. Drafts create no PMSchedule and no PMTask, so they must not appear in Assign PM, Record PM, Calendar, Dashboard or Reports.
SendCreates one pending change for the asset with proposedState.addToPlan = true and a snapshot of its drafts. Requires at least one draft. While a Send is open the machine is locked: edit, activate/deactivate, add or remove draft PM types are refused ("This machine is waiting for approval. Withdraw the request to change it.").
WithdrawSender or an approver may withdraw an open Send. The request is closed, the machine unlocks and its drafts are unchanged.
ApproveIn one transaction: set the plan-status to In plan, create the PMSchedule/PMTask for each snapshot item (unique (assetId, normalizedFrequency) rule applies, 409 per item), delete the drafts, write audit lines Added machine to Master Plan and Added <freq> PM, and save one revision per batch. A missing machine fails the item and the request stays pending. A machine already in plan resolves with no revision and no audit row. A failed item must roll back for that machine only.
RejectReason required. The machine unlocks, drafts stay, and the last rejection reason is shown on the machine until a newer Send replaces it.
After approvalThe machine is In plan: every later change (edit, deactivate, add or remove PM type) goes through the normal approval card flow above.

Open gaps

GapDetail
Cross-user persistence (blocker)Create PM (for an in-plan machine), Remove PM Type, Send to Master Plan and edits of in-plan machines all submit to the in-memory queue. Not-in-plan machines and their draft PM types are also frontend-only today. A different user (or a reload) cannot see or approve them. Until the endpoints above exist, nothing submitted survives a reload and an engineer's request can never reach a manager on another browser.
Approve creates the PMOn approving an add-PM-type card that has newPmTypeDetails, the frontend currently calls createSchedule / createTask itself as the approver, using the submitter as createdBy. Backend should do this server-side in the same transaction as the approval, enforce the unique (assetId, normalizedFrequency) rule (section 2), and return 409 per item if it now conflicts. Cards without details (dev seed only) create a local mock PM.
Pending duplicate ruleFrontend blocks a second Create PM for an asset+frequency that already has a pending add card. Backend should enforce the same at submit time.
Remove-PM-typeManage Machines now has a Remove PM Type action. Approval applies removePmScheduleType(): PUT schedule { isActive:false } then cancels not-Done/Cancelled tasks of that frequency (cancelledReason: 'PM type removed'). Whether the backend accepts isActive on a schedule update is unconfirmed. Depends on #5 PMSchedule.isActive.
Version snapshotsPM Master Plan has a Version dropdown. A snapshot holds only Asset[], so the page labels it "Machine list as of Rev X. PM marks are live and are not versioned." A real version history needs per-machine active PM types (schedules) stored in each revision.
PersistencePending changes, versions and client-only audit entries are in-memory. Backend table(s) needed once the design settles.
