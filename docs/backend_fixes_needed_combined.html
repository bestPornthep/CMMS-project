1. Duplicate PM Type Hard Block

An asset may only ever have one PM per frequency (status doesn't matter, even Done counts). Must be enforced server-side — frontend check is best-effort only and not race-safe.

Endpoint(s)POST /pm-tasks/schedule, POST /pm-tasks
Key requirementDB-level UNIQUE(assetId, normalizedFrequency) constraint — not a check-then-insert (race condition between two users creating at once).
Response on conflict409 Conflict with the conflicting task's id/status/assignee.
GotchaCustom durations equivalent to a preset (e.g. 1 month(s) = Monthly) must also collide — normalize with the same alias table + lowercase/trim as the frontend.
Race-condition safety (critical)Two users submitting the same asset+frequency at once must not both succeed — the unique constraint (not an application-level check) is what actually guarantees this; catch the DB conflict and translate it to the 409 above.

2. Checklist Change Audit Trail

Adds a human-readable diff (changes: string[]) to the audit log entry written when a series checklist is edited. This requires the series-checklist-edit capability to exist first — treat it as step 0 of this same feature, not a separate deliverable.

Step 0 — enable editingReuses existing PUT /pm-tasks/schedule/:seriesId, now correctly scoped (where: scheduleId = seriesId AND status != 'Done') since the mass-corruption bug was fixed. Updates the PmSchedule template + every non-Done task in the series; Done tasks are never touched.
Diff basisBag-of-items match on exact text — reordering alone is not a change.
Output examplesAdded: '...', Removed: '...', Added/Removed photo requirement: '...', same for value requirement.
No-op ruleIf the diff is empty, don't write an audit entry at all.

3. Engineer Product-Create Permission

POST /api/v1/products returns 403 Forbidden for Engineers today. Product owner confirmed Engineers should be allowed (matches the frontend's Create PM inline product-creation flow, already gated on pm.create.submit, which Engineers have).

Role checkAllow admin, manager, and engineer. Technicians still excluded (never have pm.create.submit).
Also requiredAssign a creator-ownership row on create, so the new product immediately shows up in the creating Engineer's ownedProducts — otherwise they can create it but can't use it, and the next step (creating an Asset under it) fails too.
ScopePermission + ownership-row-insert fix only — no schema change expected, no frontend change needed once shipped.
