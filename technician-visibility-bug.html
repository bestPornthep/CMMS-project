Bug Report — Technicians See No Assigned PM Tasks

Reported against the live server http://10.144.15.76:3000. Affects GET /api/v1/pm-tasks and GET /api/v1/pm-tasks/:id in backend/src/pm-tasks.controller.ts. Impacts the technician Dashboard, Calendar, and Record/Execute pages equally, since all three read from the same endpoint.
Assigned PM tasks vanish for the technician who owns them
Priority: High Bug

Symptom

Engineer/manager assigns a PM task to a technician (status becomes In Progress, assignedTo set to the technician's employeeId). When that technician logs in, the Dashboard shows "nothing to do" and the Calendar shows no entries — even though the task is clearly assigned to them.

Reproduction (verified live, exact accounts used)

Step 1: Logged in as ENG-TST-1 (engineer) and assigned a PM task to TECH-TST-1 via the normal Assign flow. Task status correctly becomes In Progress with assignedTo: "TECH-TST-1".

Step 2: Logged in as ADM001 (admin) and called GET /pm-tasks to confirm server-side state: 5 tasks are currently assigned to TECH-TST-1, all status: "In Progress", department Test (e.g. PM-TES-0002, PM-TES-0007, PM-TES-0026, PM-TES-0028, PM-TES-0103). So the assignment itself saved correctly.

Step 3: Logged in as TECH-TST-1 (technician, the assignee) and called GET /pm-tasks: request returns HTTP 200 with an empty array — 0 tasks. No exception, no error message, nothing in the response to indicate a problem.

Why no error appears

This is not a thrown exception, so it won't show up in server error logs or return a non-200 status — that's why it can look like "nothing is wrong" from the backend side. The request succeeds and returns a syntactically valid, empty list. The bug is in the Prisma where clause construction (below): it silently filters out every row instead of failing loudly. The only way to see it is to compare the admin's view of "who a task is assigned to" against that same technician's own GET /pm-tasks result, as done in Step 2 vs Step 3 above.

Root Cause

Technicians never own products in this data model — every seeded technician has ownedProducts: [] (see backend/prisma/seed.ts). Their access to a task comes only from assignedTo matching their employeeId (or a delegated product). But getAll() in pm-tasks.controller.ts applies a product-ownership filter to every non-admin/manager role before adding the technician's assignment filter:

if (!accessibleProducts.includes('*')) {
  where.productId = productId ? productId : { in: accessibleProducts }; // accessibleProducts = [] for technicians
}
if (user.baseRole === 'technician') {
  where.OR = [
    { assignedTo: user.employeeId },
    { productId: { in: delegated } },
  ];
}

Prisma ANDs all top-level keys in a where clause. So the final query becomes:

WHERE productId IN () AND (assignedTo = 'TECH-TST-1' OR productId IN (delegated))

productId IN () can never match any row, so the query always returns zero results for a technician with no delegations — regardless of what's actually assigned to them.

The same broken response feeds every technician-facing view — this is one bug, not three.

The same pattern exists in getOne() (used when opening a single task, e.g. from a calendar click or notification): it throws ForbiddenException based on accessibleProducts.includes(t.productId) — which is also empty for technicians — before ever checking whether the task is assigned to them.

Fix

For the technician role, skip the product-ownership restriction entirely and rely only on the assignment/delegation check. Engineer, manager, and admin logic is unaffected.

getAll() — replace:

if (!accessibleProducts.includes('*')) {
  if (productId) {
    if (!accessibleProducts.includes(productId)) {
      throw new ForbiddenException(`Product access denied for ${productId}`);
    }
    where.productId = productId;
  } else {
    where.productId = { in: accessibleProducts };
  }
}

if (user.baseRole === 'technician') {
  where.OR = [
    { assignedTo: user.employeeId },
    { productId: { in: delegated } },
  ];
}

with:

if (user.baseRole === 'technician') {
  // Technicians never own products — access is governed solely by
  // assignment or delegation, not by ownedProducts/accessibleProducts.
  where.OR = [
    { assignedTo: user.employeeId },
    { productId: { in: delegated } },
  ];
  if (productId) where.productId = productId;
} else if (!accessibleProducts.includes('*')) {
  if (productId) {
    if (!accessibleProducts.includes(productId)) {
      throw new ForbiddenException(`Product access denied for ${productId}`);
    }
    where.productId = productId;
  } else {
    where.productId = { in: accessibleProducts };
  }
}

getOne() — replace:

if (!accessibleProducts.includes('*') && !accessibleProducts.includes(t.productId)) {
  throw new ForbiddenException(`Access denied for product ${t.productId}`);
}

if (user.baseRole === 'technician' && t.assignedTo !== user.employeeId && !delegated.includes(t.productId)) {
  throw new ForbiddenException(`Task ${id} is not assigned to you`);
}

with:

if (user.baseRole === 'technician') {
  if (t.assignedTo !== user.employeeId && !delegated.includes(t.productId)) {
    throw new ForbiddenException(`Task ${id} is not assigned to you`);
  }
} else if (!accessibleProducts.includes('*') && !accessibleProducts.includes(t.productId)) {
  throw new ForbiddenException(`Access denied for product ${t.productId}`);
}
