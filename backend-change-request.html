Change Request — Recurring PM Assignment Doesn't Persist Across Future Occurrences

Affects PUT /api/v1/pm-tasks/:id in backend/src/pm-tasks.controller.ts, used by the PM Assign page's single-task Assign button and bulk-assign action.
Assigning one occurrence of a recurring PM series doesn't assign the rest of the series
Priority: High Change Request

Symptom

A recurring PM schedule (e.g. Monthly) already maintains a rolling ~1-year buffer of Pending task rows via the nightly SchedulerService.topUpSchedules() job. When an engineer assigns the current month's occurrence to a technician, next month's occurrence (and every month after that) still shows up unassigned — the engineer has to manually re-assign the same series every single period, indefinitely.

Root Cause

PUT /pm-tasks/:id only ever updates the single task row being edited. It never writes to the parent PmSchedule.assignedTo field. SchedulerService.topUpSchedules() creates each new occurrence with assignedTo: schedule.assignedTo — but since that field is never set by the assign action, it stays null forever, so every newly-generated occurrence (and every occurrence already sitting in the buffer) comes out unassigned.

Desired Behavior

Assigning any one occurrence of a recurring series should assign the entire series, permanently:

  • Set PmSchedule.assignedTo so every occurrence the nightly job generates from now on automatically inherits the technician.
  • Immediately backfill every already-existing sibling task in that series that is still Pending or Overdue (i.e. not yet started or completed) with the same assignedTo — so the months already sitting in the 1-year buffer don't require a second manual assignment.
  • This should apply identically whether the assignment comes from the single-task "Assign" button or the "Assign Selected" bulk-assign action (both call this same endpoint).

Suggested Fix

In update() (PUT /pm-tasks/:id), after the existing task update, add:

if (body.assignedTo && existing.scheduleId) {
  await this.prisma.pmSchedule.update({
    where: { id: existing.scheduleId },
    data: { assignedTo: body.assignedTo },
  });

  await this.prisma.pmTask.updateMany({
    where: {
      scheduleId: existing.scheduleId,
      id: { not: id },
      status: { in: ['Pending', 'Overdue'] },
    },
    data: { assignedTo: body.assignedTo },
  });
}

No schema change is needed — PmSchedule.assignedTo already exists in schema.prisma.

Scope note: only series created with a real scheduleId (the current/only path the frontend uses to create schedules, per the existing comment in pm-tasks.controller.ts around the schedule-creation endpoint) are covered. Legacy [SeriesID: xxx]-only series without a matching PmSchedule row are already-documented technical debt and are not part of this request.

Files touched: backend/src/pm-tasks.controller.ts (update handler only). No frontend changes needed for this part — the PM Assign page and PM Calendar already read assignedTo directly and will pick up the fix automatically once deployed.

Verify

  • Create a Monthly recurring PM, assign the first occurrence to a technician.
  • GET /pm-tasks?scheduleId=<id> should show every Pending/Overdue sibling task with assignedTo set to that technician.
  • A newly-generated occurrence (after the next nightly top-up run) should also come out pre-assigned.
  • Regression: assigning a one-time (non-recurring) PM task — no scheduleId — behaves exactly as before (only that single task is updated).
Reassigning a series to a different technician
Priority: Medium Change Request

Context

The frontend is adding a "Reassign" action (Assigned PM Work Orders tab) that lets an engineer/manager change the technician on an already-assigned recurring series — e.g. the original technician left the team or is overloaded. It calls the exact same PUT /pm-tasks/:id endpoint as the initial assignment, just with a different assignedTo value on an already-assigned task.

Good news — no extra backend code needed

The suggested fix above is not conditioned on the task/schedule having been previously unassigned — it runs any time body.assignedTo is set on a task with a scheduleId, regardless of what PmSchedule.assignedTo was before. So reassigning Just Works with the same code: it overwrites PmSchedule.assignedTo with the new technician, and backfills every Pending/Overdue sibling to the new technician as well.

One scope clarification to confirm

The backfill in the suggested fix only touches sibling tasks with status Pending or Overdue — it intentionally does not touch a sibling that's already In Progress, Pending Approval, or Done under a different technician (an edge case where two occurrences of the same series happen to be active at once). The task actually being reassigned (the one identified by :id in the URL) is always updated directly regardless of its own status, since that's just the normal single-task update path — only the other siblings are status-gated. Please confirm this matches expectations; if a different behavior is needed for that edge case, let us know before implementing.

Verify

  • With a series already assigned to Tech A, reassign the current occurrence to Tech B.
  • Confirm all Pending/Overdue siblings in the series now show assignedTo = Tech B, and PmSchedule.assignedTo = Tech B.
  • Confirm a newly-generated occurrence (next nightly top-up) also comes out assigned to Tech B, not Tech A.
