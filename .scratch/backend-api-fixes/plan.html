T3 — Fix GET /audit-logs department filter + admin lockout bug

Query param silently dropped, and admin is wrongly blocked from viewing audit logs
Priority: Medium

Problem 1: Frontend sends GET /api/v1/audit-logs?department=X for engineer/manager roles. AuditLogsController destructures @Query('type'), @Query('from'), @Query('actorId') — never @Query('department'). Result: engineers/managers see audit logs from every department, not just their own.

Problem 2 (confirmed in code): the role guard is an exclusion check —

if (user.baseRole !== 'engineer' && user.baseRole !== 'manager') {
  throw new ForbiddenException('Only engineers and managers can view audit logs');
}

— which also blocks admin. This is an access-control bug, not intentional design: locking the highest-privilege role out of the audit trail undermines its purpose (incident review, compliance). Fixing alongside the department filter since it's the same controller/handler.

Plan

  • Add department String? @map("department") to the AuditLog Prisma model + migration.
  • Add a department: string | null param to CmmsService.logAction(); update all 6 call sites (delegations.controller.ts ×2, templates.controller.ts ×3, scheduler.service.ts ×1) to pass the relevant department (typically actor.department).
  • Add @Query('department') department?: string to AuditLogsController.getAll() and filter where.department = department when provided.
  • Change the role guard to allow admin in addition to engineer/manager; technician remains blocked.
  • Existing rows will have department: null — not backfilled in this ticket.

Files touched: backend/prisma/schema.prisma, new migration, backend/src/cmms.service.ts, backend/src/audit-logs.controller.ts, backend/src/delegations.controller.ts, backend/src/templates.controller.ts, backend/src/scheduler.service.ts.

T4 — Wire /pm-tasks/schedule into the real PmSchedule model

Confirmed real bug: recurring PM series silently stop generating after ~1 year
Priority: High — upgraded after cross-checking backend_schedule_spec.md

Problem, confirmed by reading the actual current code (not just the frontend contract):

  • CmmsService.calculateDates() generates at most 1 year of future tasks in one batch (maxTasks = 365, hard stop at oneYearFromNow).
  • SchedulerService.topUpSchedules() (nightly cron) is supposed to keep refilling that rolling 1-year buffer forever — but it only works by reading this.prisma.pmSchedule.findMany(), i.e. it only tops up series that have a row in cmms_pm_schedules.
  • PmTasksController.createSchedule() — the handler actually mounted at POST /api/v1/pm-tasks/schedule, which is the only path the frontend calls (ApiService.createSchedule()) — never inserts a PmSchedule row. It only creates PmTask rows with [SeriesID: xxx] baked into description, and never sets scheduleId (the FK column already exists on PmTask and is already wired through CreatePmTaskDto / createTaskWithRetry — just never populated by this handler).

Net effect: every recurring PM schedule a user creates today gets its first ~365 days of tasks, then silently stops — the nightly top-up job can't see it because there's no PmSchedule row to top up. This will surface in production as "PM tasks just stopped appearing" roughly a year after go-live, with no error anywhere.

The PmSchedulesController resource (proper FK-based) is never called by the frontend today.

Plan — make the path the frontend already calls do this correctly, no frontend changes required

  • Rewrite PmTasksController.createSchedule() (mounted at POST /pm-tasks/schedule) to reuse PmSchedulesController's logic: create a real PmSchedule row first, then create tasks with scheduleId set to that row's id. Same response shape as today (frontend doesn't need changes — it doesn't read the schedule id back).
  • Rewrite PmTasksController.updateSchedule() (mounted at PUT /pm-tasks/schedule/:seriesId) to treat :seriesId as the PmSchedule.id, look it up directly, update the PmSchedule row, and bulk-update pending PmTask rows via scheduleId FK — dropping the string search entirely.
  • Delete the now-fully-duplicated PmSchedulesController (pm-schedules.controller.ts) since its logic is merged into the path frontend actually uses — avoids maintaining two copies. (Flagged below — confirm before deleting.)
  • Existing rows already in the DB with legacy [SeriesID: xxx] text and no scheduleId will NOT be retroactively migrated by this ticket (would need a one-off data migration script — separate ticket if wanted).

Files touched: backend/src/pm-tasks.controller.ts, possibly delete backend/src/pm-schedules.controller.ts, backend/src/app.module.ts (remove controller registration).

Verify: Create a recurring PM via pm-create → all generated tasks share one real scheduleId (check DB, not description text). Edit the series from pm-assign → all pending tasks under that scheduleId update correctly, done/approved tasks untouched.

T5 — Add isDefault to Template schema

Frontend's dedup logic checks a field that never exists on API-sourced templates
Priority: Low-Medium

Problem: Template frontend interface has isDefault?: boolean; cmms_templates table has no such column, so it's always undefined on anything from the API. pm.service.ts currently mock-injects "default" templates client-side to compensate.

Plan (backend half only — frontend mock removal is a separate, later change)

  • Add isDefault Boolean @default(false) @map("is_default") to Template model in schema.prisma, matching the column backend_spec.md already documents.
  • Generate + apply Prisma migration.
  • Seed the current hardcoded default templates (from pm.service.ts) into cmms_templates with isDefault: true, one row per department, via backend/prisma/seed.ts.
  • TemplatesController.create(): regular users cannot set isDefault: true (ignore/force false unless admin).

Not in scope for this ticket: removing the client-side mock defaults from pm.service.ts — that's a frontend change and should happen in a follow-up once this data exists in the DB, to avoid a window where defaults disappear.

Files touched: backend/prisma/schema.prisma, new migration, backend/prisma/seed.ts, backend/src/templates.controller.ts.
